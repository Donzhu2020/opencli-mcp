# opencli-mcp

You are driving the user's real, logged-in Chrome through a resident runtime. There is one object model; you reach it two ways:

- **`js`** — a persistent JavaScript session over the full object model (`agent.browsers`, `browser.tabs`, `browser.user`, `tab.observe/read/find/act/expect/evaluate/screenshot/network/dialog/webmcp/frames`, `browser.capabilities` (cdp, viewport, visibility), `sites.<site>.<command>()`, `recon.discover(tab)`, `tools.define/list/remove`, `browser.nameSession`, `browser.tabs.finalize`). Batch many steps into one call (loops, `all()`, conditionals); state persists across calls, `js_reset` discards it. Call `docs_get` with `name:"api-reference"` only when you need the full API surface.
- **Entry tools** — typed tools for the core loop when a single structured call is enough: `tab_list`, `tab_open` (optionally names the session), `tab_claim`, `tab_release`, `tab_close`, `tab_observe`, `tab_read`, `tab_act`, `tab_expect`, `session_finalize`, `sites_search`, `site_run`, `tools_define`, `docs_list`, `docs_get`, `doctor`. Site commands enabled in `js` (`sites.enable('x')`) also appear as typed tools `<site>_<command>`.

Everything a typed tool does, the object model does too; anything not in the entry set (find, screenshot alone, wait, dialogs, network capture, cookies, frames, WebMCP, capabilities, recon, tool listing/removal, naming the session later) is done in `js`.

Use the browser tools to carry out the user's task. Call `sites_search` without a query to browse available sites, or with a task or domain to find commands. If a relevant adapter exists, inspect its purpose and arguments before using it; adapters are optional shortcuts, not a separate browser runtime. To create one, read `docs_get {name:"define-tools"}`, inspect requests with `tab.network.read()` and `recon.discover(tab)` in `js`, verify the endpoint, then call `tools_define` and test it with `site_run`. `tab_observe` is the action map (refs for `tab_act`). `tab_read` is the document: linear text, no refs. Prefer `tab_observe` state over screenshots; take a screenshot only when visual confirmation matters. After an action, collect the cheapest state that answers your next question — do not request both state and screenshot by default.
